# 스키마의 이력

Alembic 이 DDL 의 기록입니다. `backend/app/models/` 의 SQLAlchemy 메타데이터가
여전히 출처이고 — 여기 있는 리비전들은 그 메타데이터로부터 만들어졌습니다.

## 파일

- `env.py` — Alembic 이 붙는 자리. `app.core.db` 에서 **살아 있는**
  `DATABASE_URL` 을 읽습니다 — `.ini` 에 박힌 값이 아니라요. 그래서 마이그레이션과
  서버가 항상 같은 데이터베이스를 봅니다.
- `versions/` — 리비전 파일. `0001_initial` 부터 시작합니다.
- `../alembic.ini` — 설정. `script_location` 이 저장소를 가리켜서 어느
  디렉터리에서 실행해도 같은 곳을 봅니다.

## 쓰는 법

```bash
make db-current        # 지금 어느 리비전인가
make db-history        # 이력
make db-check          # 모델과 리비전이 어긋났는지 (어긋나면 실패)
make db-migrate        # 현재 리비전까지 올리기
make db-revision m="설명"   # 모델을 바꾼 뒤 새 리비전 쓰기
```

서버를 다시 켜도 됩니다 — 서버가 기동할 때 스스로 `upgrade head` 합니다.
배포는 "코드 교체 + 재시작" 한 번입니다.

## 규칙

- **한 번에 하나.** 서버가 스키마를 고치는 동안 다른 프로세스가 같은
  데이터베이스를 고치면 서로의 작업을 엎습니다. 한 인스턴스만 띄운 채로
  배포를 끝내고 나서 나머지를 올리세요.
- **되돌릴 수 있습니다.** 마이그레이션은 되돌릴 수 있습니다 — 서버를 내리고
  `make db-migrate` 를 다시 실행하세요. 되돌릴 수 없는 리비전을 쓴다면
  그 사실을 커밋 메시지에 적어 둡니다.
- **데이터는 건드리지 않습니다.** 리비전은 모양만 바꿉니다. 예전 데이터베이스를
  처음 받아들이는 경우에도(`stamp`) 행은 그대로 남습니다.

## 모델을 바꿨다면

1. 모델을 고칩니다.
2. `make db-revision m="설명"` — 새 리비전 파일이 생깁니다.
3. 내용을 읽어 봅니다. 자동 생성은 가끔 엉뚱한 것을 씁니다.
4. `make db-check` — 어긋남이 없는지 확인합니다.
5. 테스트를 돌립니다.

`backend/tests/test_migrations.py` 가 이 흐름을 지켜봅니다 — 새 리비전을
쓰고 빼먹지 않았는지, 예전 데이터베이스를 받아들이면서 데이터가
남는지, 서버가 리비전보다 뒤처진 데이터베이스를 올리는지.
